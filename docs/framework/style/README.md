# SpecFirst Style Guide

## Overview

This guide defines the coding and documentation style standards for the SpecFirst framework, ensuring consistency and maintainability across all projects. The framework emphasizes **specification-driven development**, **AI/LLM code generation**, **PERA cycles**, and **TDD as quality assurance** style patterns.

## Specification-Driven Style Guidelines

### 1. Specification Documentation Style
```javascript
// Specification file naming: SPECIFICATIONS.md
// Specification structure: Clear, LLM-regenerable format
const specification = {
    feature: "User Registration",
    requirements: [
        "Accept email and password",
        "Validate email format",
        "Create user account",
        "Return user object"
    ],
    successCriteria: [
        "Valid email creates account",
        "Invalid email returns error",
        "User object contains email and status"
    ],
    constraints: [
        "Email must be valid format",
        "Password must be at least 8 characters"
    ]
};
```

### 2. PERA Cycle Documentation Style
```javascript
// PLAN: Document specification clearly
/**
 * User Registration Feature Specification
 * 
 * Plan: Create user registration system with email validation
 * Requirements: Email validation, account creation, user object return
 * Success Criteria: Valid registration, error handling, proper response format
 */

// EXECUTE: Document AI generation process
/**
 * Generated Code: registerUser function
 * Source: AI generation from specification
 * Validation: TDD ensures quality and correctness
 * Date: 2025-06-20
 */

// REPORT/REVIEW: Document validation results
/**
 * Validation Results:
 * - All tests pass: ✅
 * - Specification alignment: ✅
 * - User feedback: Positive
 * - Quality metrics: 90%+ coverage
 */

// ADJUST: Document refinements
/**
 * Specification Refinements:
 * - Added password strength validation
 * - Enhanced error messages
 * - Improved user feedback
 * - Updated based on user testing
 */
```

### 3. AI/LLM Code Generation Style
```javascript
// Generated code header
/**
 * Generated by AI from specification: User Registration
 * Specification Version: 1.0.1
 * Generation Date: 2025-06-20
 * Validation: TDD Quality Assurance
 * 
 * @param {Object} userData - User registration data
 * @param {string} userData.email - User email address
 * @param {string} userData.password - User password
 * @returns {Object} Created user object
 * @throws {Error} If email is invalid or user creation fails
 */
function registerUser(userData) {
    // AI-generated implementation
    if (!isValidEmail(userData.email)) {
        throw new Error('Invalid email format');
    }
    return {
        email: userData.email,
        isActive: true,
        createdAt: new Date()
    };
}
```

## TDD Quality Assurance Style Guidelines

### 1. TDD for AI-Generated Code Style
```javascript
// Test file naming: test_<module_name>.js
// Test function naming: test_<function_name>_<scenario>
function testRegisterUserWithValidData() {
    const userData = {email: 'test@example.com', password: 'secure123'};
    const user = registerUser(userData);
    expect(user.email).toBe('test@example.com');
    expect(user.isActive).toBe(true);
}

function testRegisterUserWithInvalidEmail() {
    const userData = {email: 'invalid', password: 'secure123'};
    expect(() => registerUser(userData)).toThrow('Invalid email format');
}

function testRegisterUserWithEmptyData() {
    const userData = {};
    expect(() => registerUser(userData)).toThrow('Email is required');
}
```

### 2. Test Organization Style
```javascript
// Group related tests in describe blocks
describe('User Registration (AI-Generated)', () => {
    test('should register valid user', () => {
        const userData = {email: "test@example.com", password: "secure123"};
        const user = registerUser(userData);
        expect(user.email).toBe("test@example.com");
        expect(user.isActive).toBe(true);
    });
    
    test('should reject invalid email format', () => {
        const userData = {email: "invalid", password: "secure123"};
        expect(() => registerUser(userData)).toThrow("Invalid email format");
    });
    
    test('should reject duplicate email', () => {
        const userData = {email: "existing@example.com", password: "secure123"};
        expect(() => registerUser(userData)).toThrow("Email already exists");
    });
});
```

## Incremental Development Style

### 1. Small Change Style
```javascript
// Change 1: Basic functionality
function processData(data) {
    return data.toUpperCase();
}

// Change 2: Add validation
function processData(data) {
    if (typeof data !== 'string') {
        throw new TypeError("Data must be a string");
    }
    return data.toUpperCase();
}

// Change 3: Add options
function processData(data, formatType = "upper") {
    if (typeof data !== 'string') {
        throw new TypeError("Data must be a string");
    }
    
    if (formatType === "upper") {
        return data.toUpperCase();
    } else if (formatType === "lower") {
        return data.toLowerCase();
    } else {
        throw new Error("Unsupported format type");
    }
}
```

### 2. Phase-Based Style
```javascript
// Phase 1: Core implementation
class UserManager {
    createUser(email) {
        return new User(email);
    }
}

// Phase 2: Add validation
class UserManager {
    createUser(email) {
        if (!this._isValidEmail(email)) {
            throw new Error("Invalid email format");
        }
        return new User(email);
    }
    
    _isValidEmail(email) {
        return email.includes("@");
    }
}

// Phase 3: Add persistence
class UserManager {
    constructor(database) {
        this.database = database;
    }
    
    createUser(email) {
        if (!this._isValidEmail(email)) {
            throw new Error("Invalid email format");
        }
        
        const user = new User(email);
        this.database.save(user);
        return user;
    }
}
```

### 3. Feedback Integration Style
```javascript
// Initial implementation
function calculateDiscount(price, discountPercent) {
    return price * (discountPercent / 100);
}

// After user feedback: Add minimum discount
function calculateDiscount(price, discountPercent, minDiscount = 0) {
    const discount = price * (discountPercent / 100);
    return Math.max(discount, minDiscount);
}

// After more feedback: Add maximum discount
function calculateDiscount(price, discountPercent, minDiscount = 0, maxDiscount = null) {
    let discount = price * (discountPercent / 100);
    discount = Math.max(discount, minDiscount);
    
    if (maxDiscount !== null) {
        discount = Math.min(discount, maxDiscount);
    }
    
    return discount;
}
```

```javascript
 *

    const validationResults = {

        missingFiles: [],
        extraFiles: []
    };
    
    // Validation logic here
    
    return validationResults;
}
```

### 2. Error Handling Style
```javascript
function processUserInput(data) {
    try {
        // Validate input
        if (!data) {
            throw new Error("Input data cannot be empty");
        }
        
        if (typeof data !== 'object') {
            throw new TypeError("Input data must be an object");
        }
        
        // Process data
        const result = processDataInternal(data);
        
        // Validate output
        if (!result) {
            throw new Error("Processing failed to produce valid result");
        }
        
        return result;
        
    } catch (error) {
        // Log error for debugging
        console.error(`Input validation failed: ${error.message}`);
        // Re-throw with user-friendly message
        throw new Error(`Invalid input: ${error.message}`);
    }
}
```

### 3. Documentation Validation Style
```javascript
/**
 * Validate that documentation matches specifications.
 * 
 * @param {string} specFile - Path to specifications file
 * @param {Array<string>} docFiles - List of documentation file paths
 * @returns {Object} Validation results with missing documentation
 * 
 * @example
 * const result = validateDocumentationCompleteness("SPECIFICATIONS.md", ["README.md"]);
 * console.log(result.missing); // ['docs/api/README.md', 'docs/user/guide.md']
 */
function validateDocumentationCompleteness(specFile, docFiles) {
    const specRequirements = extractDocRequirements(specFile);
    const existingDocs = analyzeDocumentation(docFiles);
    
    const missingDocs = specRequirements.filter(doc => 
        !existingDocs.includes(doc)
    );
    
    return {
        complete: missingDocs.length === 0,
        missing: missingDocs,
        guidance: generateDocGuidance(missingDocs)
    };
}
```

## Common Style Mistakes to Avoid

### 1. TDD Style Mistakes
- ❌ **Poor test names**: Using vague test function names
- ❌ **Complex test setup**: Making tests too complex to understand
- ❌ **Testing implementation details**: Testing how instead of what
- ❌ **Missing test documentation**: Not documenting test purpose
- ❌ **Inconsistent test structure**: Not following consistent patterns

### 2. Incremental Development Style Mistakes
- ❌ **Large functions**: Writing functions that do too much
- ❌ **Poor change documentation**: Not documenting what changed
- ❌ **Inconsistent naming**: Not following naming conventions
- ❌ **Mixed concerns**: Combining unrelated functionality
- ❌ **Poor error handling**: Not handling errors consistently

### 3. Validation Style Mistakes
- ❌ **Silent failures**: Not reporting validation errors clearly
- ❌ **Inconsistent error messages**: Using different error formats
- ❌ **Poor error context**: Not providing enough error information
- ❌ **No recovery guidance**: Not suggesting how to fix errors
- ❌ **Hardcoded validation**: Not using configuration-driven validation
